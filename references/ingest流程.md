# /wiki:ingest 执行流程

本文件是 `/wiki:ingest` 命令的完整执行规范。执行时严格按 Step 顺序进行，不可跳步，不可重排。

---

## 前置说明

- **目标**：将 `原始资料/待处理/` 中的文件提取知识，追加到知识库的相应 wiki 页面
- **核心原则**：先追加，后合并。ingest 时**只**操作 `📥 待合并内容` 区，不修改 `📖 知识摘要` 区
- **原始资料目录只读**：只允许将文件移动到 `已处理/`，不允许修改原始文件内容

---

## Step 1：读取配置文件

1. 在当前工作目录查找 `wiki配置.json`
2. 若找不到，输出错误提示：
   ```
   ❌ 未找到 wiki配置.json，请先运行 /wiki:init 初始化知识库
   ```
   然后**中止执行**。
3. 解析配置，提取以下字段：
   - `知识库路径`（默认 `./知识库`）
   - `原始资料路径`（默认 `./原始资料`）
   - `卡片路径`（可为 `null`）
   - `卡片格式`（可为 `null`）
4. 将相对路径解析为基于 `wiki配置.json` 所在目录的绝对路径。
5. 验证以下目录存在，若不存在则报错并中止：
   - `<原始资料路径>/待处理/`
   - `<知识库路径>/索引/`

---

## Step 2：扫描待处理目录

1. 列出 `<原始资料路径>/待处理/` 下的所有文件（不递归子目录）。
2. 若目录为空，输出：
   ```
   ℹ️ 待处理目录为空，无文件需要处理。
   ```
   然后**中止执行**。
3. 记录文件列表，准备逐个处理。

---

## Step 3：文件类型判断

对每个文件：

| 扩展名 | 处理方式 |
|--------|----------|
| `.md` | ✅ 处理（Markdown 格式） |
| `.txt` | ✅ 处理（纯文本格式） |
| 其他（.pdf、.docx、.png 等） | ⏭️ 跳过，向用户输出提示并在操作日志中记录 |

### 3.1 非支持格式文件提示

当扫描到非 `.md`/`.txt` 文件时，**不处理该文件**，但向用户输出友好提示，建议使用对应 skill：

| 扩展名 | 提示文本 |
|--------|----------|
| `.pdf` | `⏭️ 跳过 xxx.pdf —— PDF 文件请先使用 pdf skill 转换为 .md 后再放入待处理目录` |
| `.docx` | `⏭️ 跳过 xxx.docx —— Word 文件请先使用 docx skill 转换为 .md 后再放入待处理目录` |
| `.png` / `.jpg` / `.jpeg` / `.gif` | `⏭️ 跳过 xxx.png —— 图片文件请先使用 ocr skill 提取文字为 .md 后再放入待处理目录` |
| 其他 | `⏭️ 跳过 xxx.ext —— 不支持的格式，请转换为 .md 或 .txt 后再放入待处理目录` |

- 每个被跳过的文件单独输出一条提示
- 同时在操作日志中记录：`跳过文件：xxx.pdf（不支持的格式，建议使用 pdf skill）`
- 跳过的文件**不移动**，保留在 `待处理/` 目录中

---

## Step 4：提取概念与实体

对每个待处理文件，执行以下提取任务：

### 4.1 阅读理解

完整阅读文件内容，理解文章的主题、论点和关键信息。

### 4.2 提取概念列表

识别文章中涉及的**核心概念**（抽象的思想、方法、技术、理论）：
- 提取粒度：主要论点 + 关键技术概念
- 数量：每篇文章通常 2-6 个概念
- 对每个概念，整理 **3-5 条核心要点**（段落形式，不是列表）

**示例**：
- 文章讨论 Transformer → 提取概念：`Transformer`、`注意力机制`、`位置编码`
- 对每个概念，整理该文章的核心观点（而非概念的全部知识）

### 4.3 提取实体列表

识别文章中涉及的**具体实体**（可命名的人、书、工具、组织）：
- **人物**：研究员、作者、业界人物
- **论文/书籍**：被引用或讨论的作品
- **工具/框架**：软件、库、平台
- **组织/机构**：公司、研究院、团队

数量：每篇文章通常 0-5 个实体，没有则跳过实体步骤。

---

## Step 5：索引匹配（模糊匹配规则）

对每个提取的概念/实体，读取对应的索引文件进行匹配：
- 概念 → 读取 `<知识库路径>/索引/概念索引.jsonl`
- 实体 → 读取 `<知识库路径>/索引/实体索引.jsonl`

### 模糊匹配规则

判断是否为「已有概念」，按以下逻辑匹配（任一匹配即视为已有）：

1. **精确匹配**：提取的概念名与索引中的 `标题` 完全一致
2. **大小写忽略**：如 `transformer` 匹配 `Transformer`
3. **中英文等价**：如 `注意力机制` 匹配 `Attention Mechanism`（依靠 LLM 语义判断）
4. **别名匹配**：如 `自注意力` 视为 `注意力机制` 的别名（依靠 LLM 语义判断）
5. **包含关系**：若新概念是索引中某概念的明显子集（如 `多头注意力` 包含于 `注意力机制`），归入已有概念，追加时注明是子概念

**匹配不确定时**：优先归入已有概念（追加），而非新建页面（避免重复）。

---

## Step 6a：新概念/实体 → 新建页面

若该概念/实体在索引中**未找到匹配**：

1. **生成 ID**：按 `references/schema.md` 第六节的规则生成 id
2. **确定文件路径**：
   - 概念 → `<知识库路径>/概念/<id>.md`
   - 实体 → `<知识库路径>/实体/<id>.md`
3. **创建 wiki 页面**：按 `references/schema.md` 对应模板创建文件
   - `📖 知识摘要` 区：填入从本文章提取的 3-5 条核心要点（段落形式）
   - `📥 待合并内容` 区：**留空**（仅保留区标题和注释）
   - 来源字段：填入原始文件名
   - **Wikilink 自动插入**：写入 `📖 知识摘要` 内容后，执行交叉引用替换（见下方 Step 6c）
4. **追加索引条目**：在对应 `.jsonl` 文件末尾追加一行：
   - 概念：`{"id": "...", "标题": "...", "文件": "概念/xxx.md", "标签": [...], "有冲突": false, "更新时间": "YYYY-MM-DD"}`
   - 实体：`{"id": "...", "标题": "...", "类型": "...", "文件": "实体/xxx.md", "标签": [...], "更新时间": "YYYY-MM-DD"}`
5. 在操作日志记录：`新建概念页：<标题>`

---

## Step 6b：已有概念/实体 → 追加到 📥 待合并内容区

若该概念/实体在索引中**找到匹配**：

1. 读取现有 wiki 页面（路径来自索引中的 `文件` 字段）
2. **检查认知冲突**：
   - 读取 `📖 知识摘要` 区的内容
   - 判断本文章的相关观点是否与摘要中的陈述**存在实质矛盾**（不是补充，而是冲突）
   - 若有冲突 → 在追加内容末尾加上 `⚡ 认知分歧` 标注块（见 schema.md 第一节）
3. **追加到 📥 待合并内容区**：
   在页面的 `## 📥 待合并内容` 标题之后追加一条：
   ```markdown
   > **来源**：原文件名.md（YYYY-MM-DD）
   >
   > [从该文章提取的关于本概念的 3-5 条要点，段落形式]
   ```
   - **Wikilink 自动插入**：写入要点段落后，执行交叉引用替换（见下方 Step 6c）
   若有冲突，紧接在要点段落之后追加：
   ```markdown
   > ⚡ **认知分歧**
   > 外部资料认为：[外部观点简洁陈述]
   > 来源：[文件名]
   ```
4. **不修改** `📖 知识摘要` 区的任何内容
5. 在操作日志记录：`更新概念页：<标题>（新增 1 条 pending）`

---

## Step 6c：Wikilink 交叉引用替换

在 Step 6a 写入 `📖 知识摘要` 或 Step 6b 写入 `📥 待合并内容` 的文本**写入完成后**，对该段文本执行以下替换：

1. **扫描索引**：读取 `概念索引.jsonl` 和 `实体索引.jsonl`，收集所有已知 id 和标题
2. **逐一匹配**：在刚写入的文本中查找所有已知概念/实体的 `标题` 或 `id` 出现位置
3. **替换为 wikilink**：
   - 若文中使用的名称**与 id 相同**（忽略大小写），替换为 `[[id]]`
     - 示例：文中出现 `transformer` → `[[transformer]]`
   - 若文中使用的名称**与 id 不同**（如中文别名、全称等），替换为 `[[id|原文]]`
     - 示例：文中出现 `Transformer 架构` 而 id 为 `transformer` → `[[transformer|Transformer 架构]]`

4. **约束规则**（参照 `schema.md` 第七节）：
   - **首次出现**：对同一个 id，每个页面中只链接**第一次出现**，后续出现保留原文不加链接
   - **不自链接**：当前页面的 id 不对自身创建 `[[]]` 链接
   - **无路径前缀**：直接写 `[[transformer]]`，不写 `[[概念/transformer]]`
   - **不回溯**：只处理本次新写入的文本，不修改页面中已有的旧内容

---

## Step 7：卡片接口插槽

检查配置文件中的 `卡片路径` 字段：

- **若 `卡片路径` 为 `null`**：
  - 跳过所有卡片处理
  - 在操作日志记录：`卡片笔记接口未配置，已跳过`
  - **不报错**，继续执行 Step 8

- **若 `卡片路径` 非 `null`**（预留接口，当前版本未实现）：
  - 在操作日志记录：`卡片笔记接口已配置（路径：xxx），当前版本暂不处理卡片，已跳过`
  - **不报错**，继续执行 Step 8

> 📌 设计备注：卡片接口开放后，此处将读取 `卡片路径` 中的个人笔记卡片，在认知分歧标注中加入「个人笔记认为：...」的对比信息。

---

## Step 8：归档原始文件

对每个**成功处理**的文件（.md 或 .txt 类型）：

1. **确定归档路径**：`<原始资料路径>/已处理/YYYYMMDD_原文件名`
   - 日期格式：`YYYYMMDD`（如 `20260415`）
   - 示例：`transformer-intro.md` → `已处理/20260415_transformer-intro.md`
2. **移动文件**：将文件从 `待处理/` 移动到 `已处理/`
   - 若目标文件名已存在，在日期后追加 `_2`、`_3` 等序号
3. **原则**：移动操作完成后，`待处理/` 中不应再有该文件

跳过的文件（不支持格式）**不移动**，保留在 `待处理/` 中。

---

## Step 9：写操作日志 + Pending 提示

### 9.1 写操作日志

在 `<知识库路径>/操作日志.md` 末尾追加（不覆盖历史）：

```markdown
---

### [YYYY-MM-DD HH:MM] /wiki:ingest | 处理 N 个文件，新建 M 个概念，追加 K 条 pending

**处理文件**：
- `原文件名1.md` → 归档为 `已处理/YYYYMMDD_原文件名1.md`

**新建概念页**：（无 / 概念1, 概念2）
**更新概念页**：（无 / 概念名（新增 N 条 pending））
**新建实体页**：（无 / 实体1）
**更新实体页**：（无 / 实体名（新增 N 条 pending））
**跳过文件**：（无 / 文件名（不支持的格式））
**卡片接口**：卡片笔记接口未配置，已跳过

**Pending 积压统计**：共 N 条待合并内容
```

### 9.2 Pending 积压提示

统计知识库中**所有页面**的 `📥 待合并内容` 区条目总数：

- 若总数 **> 10**，在控制台和日志中追加：
  ```
  ⚠️ 积压超过 10 条，建议运行 /wiki:consolidate 进行合并整理
  ```
- 若总数 ≤ 10，无需额外提示

### 9.3 向用户展示摘要

ingest 完成后，向用户输出本次处理摘要：

```
✅ /wiki:ingest 完成

处理文件：N 个
新建页面：N 个（概念 N + 实体 N）
更新页面：N 个
跳过文件：N 个
Pending 积压：共 N 条

[如积压 > 10]
⚠️ 建议运行 /wiki:consolidate 进行合并整理
```

## 错误处理

| 情况 | 处理方式 |
|------|----------|
| `wiki配置.json` 不存在 | 中止，提示运行 /wiki:init |
| 待处理目录不存在 | 中止，提示手动检查目录结构 |
| 单个文件读取失败 | 跳过该文件，记录错误到日志，继续处理其他文件 |
| 写入 wiki 页面失败 | 记录错误到日志，不归档该原始文件（避免丢失） |
| 索引文件不存在 | 创建空的索引文件，继续执行 |

---

## 注意事项

1. **每篇文章对同一概念只追加一条 pending 条目**，不要重复追加
2. **不修改 `📖 知识摘要` 区**——这是 consolidate 的工作
3. **不合并 pending 条目**——保持原始来源可追溯
4. **同一次 ingest 处理多个文件时**，每个文件独立处理，不合并提取结果
5. 认知冲突判断要有实质性——补充信息不算冲突，互相矛盾的结论才算冲突
